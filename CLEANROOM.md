# Clean-room log

Kaho AI is built from scratch using only public documentation and first-principles engineering.
Note here any public docs or sources relied on for non-obvious decisions.

| Date | Decision | Source (public URL) |
|------|----------|---------------------|
| 2026-09-26 | Pipeline wiring (`LLMContext` + `LLMContextAggregatorPair`, `PipelineWorker` + `WorkerRunner`, service stage order) follows the templates and service registry bundled inside the installed `pipecat-ai` package (`pipecat/cli/templates/`, `pipecat/cli/registry/_configs.py`). `PipelineTask`/`PipelineRunner` are deprecated aliases in 1.12.0. | Pipecat's own shipped templates; https://docs.pipecat.ai |
| 2026-09-26 | `LocalAudioTransport` (PyAudio mic/speaker) over the CLI's WebRTC/telephony transports — stage 1 is terminal-only, no browser. Needs the `local` extra and `brew install portaudio`. | `pipecat/transports/local/audio.py` docstring; https://docs.pipecat.ai |
| 2026-09-26 | Deepgram `nova-3` with `language=multi` for Hindi/English code-switching. Verified against the live API: `nova-3` returned 200 for `multi`, `en-IN`, `en`, `hi`. Pipecat passes the unrecognized-by-its-enum `multi` through as-is. | https://developers.deepgram.com — combination confirmed empirically |
| 2026-09-26 | Groq `openai/gpt-oss-120b`. `GET /openai/v1/models` on this account lists only gpt-oss (120b/20b), `qwen/qwen3.8-27b` and `allam-2-7b` as chat models — no Llama 3.3. 120b matched 20b on latency (~0.54s) at higher quality. Measured 0.53s to first streamed token. | https://console.groq.com/docs — model list and timings measured against the live API |
| 2026-09-26 | `GROQ_REASONING_EFFORT=low`, and `LLM_MAX_TOKENS` left unset. gpt-oss models spend the `max_tokens` budget on reasoning first: at 100 tokens with no `reasoning_effort`, 120b truncated mid-sentence and 20b returned empty content. Reasoning arrives in a separate `reasoning` field, so it is never spoken. | `GroqLLMSettings` docstring in `pipecat/services/groq/llm.py`; truncation reproduced against the live API |
| 2026-09-26 | ElevenLabs `eleven_flash_v2_5`: lowest latency (~75ms class) and half the per-character credit cost of `multilingual_v2`, which roughly doubles the number of test calls a plan covers. | https://elevenlabs.io/docs |
| 2026-09-26 | `check_providers.py` validates ElevenLabs by synthesizing two characters rather than reading account metadata: a TTS-scoped key returns 401 `missing_permissions` for `/v1/user`, `/v1/models` and `/v1/voices`, so only synthesis proves it works. Free plans also reject Voice Library voices over the API with HTTP 402. | ElevenLabs API error responses observed directly; https://elevenlabs.io/docs |
| 2026-09-27 | The voice follows the caller's language per turn: `FollowCallerLanguage` reads the language Deepgram reports on each final transcript and sends the TTS a settings delta, which Sarvam applies by resending its config rather than reconnecting. Only the **streaming** socket reports it — the batch `/v1/listen` returns no `languages` field for the same audio, so testing this against batch would wrongly suggest the feature cannot work. Verified by synthesizing Hindi and English with Sarvam and streaming both back: `languages=['hi']` and `['en']`. | Measured against both Deepgram endpoints; https://developers.deepgram.com |
| 2026-09-27 | Default LLM moved to `qwen/qwen3.8-27b`. Measured on this account over 5 prompts: qwen 0.31s median TTFT (worst 0.33s), gpt-oss-20b 0.50s (0.58s), gpt-oss-120b 0.59s (**1.65s worst**), allam-2-7b 0.20s but Arabic-first and weaker on garbled input. Consistency matters as much as the median on a call, which rules out the 120b spike. No 8B-instant-class model exists on this account. | Measured against the live API; model list from `GET /openai/v1/models` |
| 2026-09-27 | The greeting is sent as a `user` message, not `developer`. Qwen's chat template rejects a conversation with no user turn (HTTP 400, "No user query found in messages"), which marks the LLM service unusable and opens the call in silence. gpt-oss tolerates `developer`, so this only appeared when swapping models — the portable role is `user`. | Reproduced live while switching models |
| 2026-09-27 | Deepgram Aura exposes no character-count buffer. The websocket sends only `model`, `encoding`, `sample_rate` and `speed`, and buffers text server-side until flushed; the `chunk_size` in Pipecat's Deepgram TTS belongs to the HTTP variant and is an audio-byte read size. The real equivalent lever is `TTS_TEXT_AGGREGATION` (sentence or token). | `pipecat/services/deepgram/tts.py`; https://developers.deepgram.com |
| 2026-09-27 | Sentence-level TTS streaming was already in place: Pipecat's `TextAggregationMode` defaults to `SENTENCE`, and a single reply was observed producing several `Generating TTS` calls. Exposed as config rather than "fixed". | `pipecat/services/tts_service.py` |
| 2026-09-27 | STT runs with `smart_format` and `numerals` on (Pipecat defaults both off), and `keyterm` driven by `DEEPGRAM_KEYTERMS`. Verified against the live API: nova-3 accepts `keyterm` under both `multi` and `en`, so term boosting costs us no code-switching; it **rejects** the older `keywords` parameter outright ("Keywords are not supported for Nova-3"). `endpointing` and `utterance_end_ms` are streaming-only and 400 on batch requests. | Parameter matrix tested directly against `/v1/listen`; https://developers.deepgram.com |
| 2026-09-27 | Markdown and typographic punctuation are stripped in code (Pipecat's `MarkdownTextFilter` plus a small `SpokenPunctuationFilter`) rather than trusted to the prompt. The prompt forbids em-dashes and the model still emitted one under test, and anything the LLM formats wrong is read aloud verbatim to the caller. Dashes take the surrounding whitespace with them, since "need—could" would otherwise become "need,could" and be slurred into one word. | Behaviour observed under test; filter API from `pipecat/utils/text/` |
| 2026-09-27 | An anti-invention rule has to be phrased as sourcing ("only state what you were given"), never as absence ("you have no hours or prices"). The absence phrasing was tried first and the clinic persona began refusing to give opening hours its own prompt listed. | Regression observed under test |
| 2026-09-27 | Superseded: the agent now replies only in English (it still understands Hindi input). Before that, the persona file, not the shared rules, decided which language the agent drifts into. With "a voice assistant for callers in India" in the persona, English questions came back in Hindi about half the time even though the rules said to match the caller; the clinic persona, which carries no Hindi cues, never drifted. Framing India as context rather than as the register fixed it. | Behaviour measured over repeated runs |
| 2026-09-27 | The system prompt lives in `apps/voice/prompts/` and is selected by `AGENT_SYSTEM_PROMPT_PATH`, with the speaking rules (`VOICE_RULES` in `main.py`) always prepended. Splitting them means a new persona describes only who the agent is, and cannot accidentally drop the constraints that keep replies speakable. | First-principles; no external source |
| 2026-09-26 | `main.py` points `SSL_CERT_FILE` at certifi when the interpreter's own CA file is missing. The python.org macOS build leaves `.../etc/openssl/cert.pem` unpopulated until you run its "Install Certificates.command", so both Deepgram websockets failed with `CERTIFICATE_VERIFY_FAILED` while plain HTTPS worked — httpx bundles certifi, the `websockets` library uses the interpreter default. Fixing it in-process keeps the repo portable instead of depending on a machine-level step. | Diagnosed from `ssl.get_default_verify_paths()` on this machine; https://docs.python.org/3/library/ssl.html |
| 2026-09-26 | TTS is switchable via `TTS_PROVIDER`, defaulting to Deepgram Aura. ElevenLabs free plans reject Voice Library voices over the API (402), which blocked every voice tried; Aura runs on the STT key we already hold and verified clean. Aura voices are English-only, so Hindi output means switching back to ElevenLabs. | Deepgram `/v1/speak` verified against the live API; https://developers.deepgram.com |
| 2026-09-28 | Smallest AI added as a fourth `TTS_PROVIDER` (`smallest`) so its Hindi voices can be A/B'd against Sarvam's, whose default Hindi voice was not liked. Uses Pipecat's `SmallestTTSService` (Lightning v3.1, websocket). Options follow the Sarvam rule: unset ones are omitted so the service's own defaults apply. `check_providers.py` checks it over the same websocket, since Pipecat's service has no REST path. Not yet run against the live API: no `SMALLEST_API_KEY` was available when it was written. | `pipecat/services/smallest/tts.py`; https://docs.smallest.ai |
| 2026-09-28 | Telephony is Plivo, inbound first, via `apps/voice/server.py`: `/answer` returns `<Stream bidirectional="true" contentType="audio/x-mulaw;rate=8000">` pointing at `/ws`, and Pipecat's `PlivoFrameSerializer` converts the 8kHz mu-law to and from PCM and sends `clearAudio` on barge-in. The pipeline is shared with the local run through `build_worker()`, so a phone call gets identical STT, LLM, TTS and turn-taking. Pipeline input is 16kHz because Silero VAD only takes 8 or 16kHz. Both routes need a `WEBHOOK_SECRET` token, chosen over Plivo's V3 signature check because a public `/ws` otherwise lets anyone spend our provider credits and the signature scheme was not verified; signature validation is the next hardening step. Verified with a simulated Plivo client (greeting audio came back as `playAudio`, hangup tore the pipeline down cleanly); **not yet with a real Plivo call**, so the real `start` event shape is unconfirmed. | `pipecat/serializers/plivo.py`, `pipecat/transports/websocket/fastapi.py`; https://www.plivo.com/docs |
| 2026-09-28 | Call transcripts are stored as text only, through `CallTranscript`, which masks Aadhaar (any 12 digits, last 4 kept) and PAN inside the single `write` method, so no caller can store an unmasked turn. Over-masking is deliberate: a masked phone number costs a follow-up, a stored Aadhaar is a breach. Turns that look like number fragments are held and masked as one run, because a live test showed Deepgram ending a turn at every pause while an Aadhaar was read out (`2 3 4` / `5 6 7` / `8 9 1` / `2 3 4,`), so per-turn masking stored the whole number in pieces. Verified end to end with synthesized speech through `/ws`: no digit or PAN letter reached the file. Known gaps: numbers STT leaves as words, and an STT-misheard PAN letter is still masked (it heard `F` as `S`). Audio is not recorded: consent is undecided. | Observed live in the Plivo smoke test; UIDAI/Income Tax formats (12 digits, `AAAAA9999A`) |
